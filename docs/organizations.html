組織構成

アカウントを役割ごとのOUにカテゴライズし、セキュリティ管理とアプリケーションワークロードを分離しています。ワークロードは環境ごとにアカウントを分け、障害や権限の影響範囲を環境内に閉じます。

AWS Organizations

OURootTerraform管理外

組織の最上位。ここに付けたSCPが配下全体に効く（managementを除く）

  • AccountmanagementTerraform管理外組織・アカウント・請求の管理

OUsecurity

セキュリティ監視・監査

  • Accountlog-archiveログの集約・長期保管
  • Accountaudit組織全体の監視・委任管理者

OUworkload

アプリケーションワークロード

  • Accounttestテスト環境
  • Accountdevelopment開発環境
  • Accountproduction本番環境

Terraform管理外managementアカウントとRoot OUは、Terraformの実行前に手動で作成する必要があるため

OUの役割

OU親役割適用するSCP※
Root-組織の最上位。全アカウント共通のガードレールを適用するguardrails、region-restriction
securityRoot組織全体のログを保管し、セキュリティの監視・監査を行うアカウントをまとめるsecurity-ou
workloadRootアプリケーションを動かすアカウントをまとめる-

※ 上位のOUに適用したSCPは配下のOUにも継承されるため、security・workloadにもRootのSCP（guardrails、region-restriction）が効く

アカウントの役割

アカウントOU役割主なサービス
managementRootOrganizationsの構成管理、アカウントの作成・招待・削除、請求・予算・コスト管理、ルートユーザーの運用。アプリケーションやワークロードは配置しないOrganizations、IAM Identity Center、Billing
log-archivesecurity全アカウントのログを集約し、改ざん・削除されないよう長期保管するConfig・CloudTrail（ログ保管用S3）
auditsecurity委任管理者として組織全体を監視し、セキュリティ通知・運用の受け皿になるConfig、GuardDuty・Security Hub（予定）
testworkloadテスト環境のワークロード-
developmentworkload開発環境のワークロード-
productionworkload本番環境のワークロード-

各アカウント内のリソース（ログ基盤、セキュリティ監視、ガバナンスなど）は、このリポジトリの2-account-baseline/で作成します。1-organization/が作るのはアカウントとOUまでです。

設定内容

AWS Organizationsは、使いたい機能を1つずつオンにする仕組みです。

ポリシー

コンソールの「ポリシー」画面に当たる設定です。オンにした種類のポリシーを、Root・OU・アカウントに付けられるようになります。

ポリシーできるようになること設定値
SCP全アカウントの操作を、OU単位で制限するSERVICE_CONTROL_POLICY

※ 1-organization/main.tfで設定する。タグのルールはタグポリシーを使わず、AWS Configで管理する（タグの方針）

信頼されたアクセス

コンソールの「サービス」→「統合されたサービス」の一覧にある、「信頼されたアクセス」の設定です。AWSサービスに組織の情報へのアクセスを許可し、組織内の全アカウントをまとめて管理できるようにします。

サービスできるようになること設定値
IAM Identity Center1か所のログインで全アカウントにアクセスし、権限を割り当てるsso.amazonaws.com
CloudTrail全アカウントの操作ログを、1つの証跡でまとめて記録するcloudtrail.amazonaws.com
Config全アカウントの設定の評価結果を集約し、ルールを全アカウントに展開するconfig.amazonaws.com
config-multiaccountsetup.amazonaws.com
GuardDuty全アカウントの脅威検知（マルウェア保護を含む）を、auditでまとめて管理するguardduty.amazonaws.com
malware-protection.guardduty.amazonaws.com
Security Hub全アカウントのセキュリティ検出結果を、auditに集約するsecurityhub.amazonaws.com

※ 1-organization/variables.tfで設定する

委任管理者

本来managementでしか行えない「組織全体を対象にしたサービスの管理」を、auditアカウントに任せます。auditから全アカウント分のサービスを有効化し、検知・評価の結果をauditに集めて確認します。各サービスの設定は、2-account-baseline/からauditアカウントで行います（現在はConfigのみ。GuardDuty・Security Hubは予定）。

サービスどんなサービスか登録単位
GuardDuty脅威の検知。CloudTrailやVPCフローログなどを分析し、不正アクセスやマルウェアなどの怪しい動きを見つけるリージョンごと
Security Hub設定のチェックと結果の集約。リソースの設定がセキュリティのベストプラクティスに沿っているかを評価し、GuardDutyなどの検知結果もまとめて1か所で見られるようにするリージョンごと
Config設定変更の記録。リソースの設定と変更履歴を記録し、ルールに沿っているかを評価する組織全体で1回

※ 1-organization/main.tfで設定する

運用手順

アカウントの追加

  1. 1-organization/security-ou/main.tfまたは1-organization/workload-ou/main.tfにアカウントを追加し、account_emailsにメールアドレスを設定する
  2. 2-account-baseline/に追加したアカウントのproviderとConfigのレコーダーを追加してapplyする（Terraformの構成を参照）
  3. 必要に応じてIAM Identity Centerのグループに新しいアカウントを割り当てる
初回のみ：既存リソースの取り込み

既存の組織、OU、アカウントは、初回のplan前にterraform importでstateへ取り込みます。手順はREADMEを参照してください。import後のplanで、以下に差分がないことを確認してからapplyします。

  • aws_service_access_principals：既に有効なサービスが含まれていないと、そのサービスの信頼されたアクセスが無効化される
  • アカウントのname、email：既存の値と異なると、アカウントの作り直しになる場合がある

注意点

  • managementアカウントのルートユーザーとAdmin権限は、組織全体を変更できる最も強い権限。MFAを必須にし、日常の作業には使わない
  • SCPはmanagementアカウントには適用されない。managementはSCPに頼らず、アクセスできるユーザーとロールを最小限に絞る
  • aws_service_access_principalsからサービスを外すと、そのサービスの信頼されたアクセスが無効化される
  • 組織から外すには、そのアカウントに支払い方法などの登録が必要。外したアカウントはmanagementから見えなくなり、課金も別になる。不要になったアカウントは、組織から外さずにmanagementから閉鎖する
  • 委任管理者のauditアカウントを変更すると、Configのアグリゲーター・組織ルールと、GuardDuty・Security Hubの集約設定もやり直しになる
